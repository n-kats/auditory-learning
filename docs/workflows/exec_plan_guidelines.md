# ExecPlan ガイドライン

このドキュメントは、長時間・高難度の開発タスクに
取り組む際に作成する ExecPlan（実行可能な設計仕様）の
書き方と運用ルールを定義します。ExecPlan は
**単独のエージェントや初心者の開発者でも、
このファイルと現在のリポジトリだけを頼りに
機能を完成させられること** を目標とした生きた
ドキュメントです。

## ExecPlan を利用するタイミング

- 大規模な機能追加、広範なリファクタリング、または
  調査が長時間に及ぶ作業では ExecPlan を必ず作成する。
- 着手前に最新の ExecPlan を読み直し、セクション構成を骨組みとして埋めていく。
- 計画実行中は次のマイルストーンへ即座に進み、進捗や
  追加の判断は ExecPlan 内で記録する。
- 作業を中断・再開するたびに ExecPlan を更新し、常に
  「これだけ読めば再開できる」状態を保つ。

## AGENTS.md への記載例

`AGENTS.md`（または同等のエージェント設定ファイル）には、
以下のように ExecPlan を参照する節を追加しておく。
ユーザーが「ExecPlan を使って」と指示すると、この
ドキュメントと整合する計画を作成・更新できる。

```md
# ExecPlan ワークフロー

複雑な機能追加や大規模リファクタリングでは、docs/workflows/exec_plan_guidelines.md に従った ExecPlan を
作成し、設計から実装まで一貫して活用する。
```

## 非交渉の必須要件

ExecPlan には以下を必ず満たさせること。

1. **自己完結性**  
   依存する前提・操作手順・検証方法をすべて記載し、
   外部リンクや担当者の暗黙知に頼らない。
2. **生きたドキュメント**  
   実装の進行・仕様変更・調査結果に応じて逐次更新し、最新状態を常に反映する。
3. **初学者でも実装可能**  
   専門用語は平易な言葉で定義し、利用ライブラリやファイル位置を明示する。
4. **動作での受け入れを定義**  
   「コードが書かれた」ではなく「どのコマンドを実行し、
   どの挙動を確認するか」を明記する。
5. **目的重視**  
   変更によりユーザーが得られる価値を冒頭で説明し、どのように確認できるかを示す。

## ExecPlan の基本構成

以下のセクションを最小構成とし、必要に応じて小見出しを
追加する。初稿では骨組みのみを置き、調査や設計を進め
ながら肉付けする。

1. **目的と意図**  
   ユーザー視点での価値と期待される挙動を数文で説明する。
2. **状況と前提整理**  
   現状把握に必要なファイルパス、モジュール構成、用語定義をまとめる。
3. **作業計画**  
   実装手順を文章で記述し、編集するファイル・関数・挿入内容を具体的に列挙する。
4. **具体的な作業手順**  
   実際に実行するコマンドと作業ディレクトリ、期待される出力例を記載する。
5. **検証と受け入れ条件**  
   受け入れ条件を動作として書き、テスト名・コマンド・期待結果を明示する。
6. **再実行性と復旧手順**  
   再実行が安全か、失敗時の巻き戻し方法や注意点を提示する。
7. **成果物と補足**  
   重要なログ・差分・スニペットを必要最小限で引用し、成功を証明する。
8. **インターフェースと依存関係**  
   追加・変更されるクラスや関数のシグネチャ、利用ライブラリを仕様として固定する。
9. **意思決定ログ**  
   変更や判断は `- 判断: ...` / `理由: ...` / `日付・担当: ...` 形式で追記する。
10. **結果と振り返り**  
    マイルストーン完了時や最終時点で成果・ギャップ・学びを簡潔に記録する。

以下は埋め込み用の Markdown テンプレート。状況に合わせて調整し、空欄を残さない。

````md
# ExecPlan: <作業名>

## 目的と意図
- 目的: …
- ユーザー価値: …
- 確認方法: …

## 状況と前提整理
- レポジトリの現状: …
- 主要ファイル/モジュール: …
- 用語定義: …

## 作業計画
1. …
2. …

## 具体的な作業手順
```bash
(作業コマンドと想定出力)
```

## 検証と受け入れ条件
- テスト/確認手順: …
- 期待結果: …

## 再実行性と復旧手順
- リトライ方法: …
- 失敗時の対処: …

## 成果物と補足
> 重要ログや抜粋

## インターフェースと依存関係
- 変更対象 API/クラス: …
- 依存ライブラリ: …

## 意思決定ログ
- 判断: …
  理由: …
  日付・担当: …

## 結果と振り返り
- 成果: …
- 課題: …
- 次のアクション: …
````

## 運用ルール

- 作業中に計画が変わった場合は理由とともに即座に ExecPlan を更新する。
- 検証用の試作や補助スクリプトもマイルストーンとして明示し、成果と学びを残す。
- 複数人で作業する場合でも単一の ExecPlan をソース
  オブトゥルースとして共有し、編集履歴で意思決定を追える
  状態に保つ。
- ExecPlan が完成し成果が反映されたら、関連ドキュメント
  （仕様書・サンプル・実装ステータス）も忘れず同期する。
